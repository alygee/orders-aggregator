# Решение

## 1. Скидки в `daily-totals`

- Миграция `002_amount_paid.sql`: колонка `orders.paid_kop` (копейки, фактически оплачено). Для уже сохранённых строк — `= amount_kop`.
- `OrdersService.normalize` читает `amountPaid` (число или строка, как и `amount`). Нет поля (у ~1/4 заказов, старый формат API) → без скидки, `paid = amount`. `amountPaid > amount` не отклоняется: иначе оплаченный заказ молча выпал бы из статистики целиком. Такой заказ сохраняется как есть, `discount` за день может стать отрицательным, и это видно в отчёте. В данных мока таких заказов нет.
- `TotalsService.daily` суммирует копейки: `gross = Σ amount`, `net = Σ amountPaid`, `discount = gross − net`, `total = gross`. В рубли переводим только на выходе, поэтому копейки сходятся точно.

**Решение:** `net` берём из `amountPaid`, а не пересчитываем из `discountPercent`. `amountPaid` — то, что реально заплатили (так требует задание), а проценты в API бывают строкой (`"7"`). На всех 3853 заказах выгрузки `amount × (1 − p/100) = amountPaid` с точностью до копейки, так что противоречий нет.

## 2. Жалоба по `c_7`

**Причина:** смещение таймзоны считалось один раз, на текущий момент (`tzOffsetMinutes(timezone, new Date())`), и применялось ко всем заказам. У `c_7` таймзона `Europe/Berlin`; 29.03.2026 там переход на летнее время (UTC+1 → UTC+2). Сейчас (ноябрь) смещение +1 ч, поэтому заказы после перехода, созданные между 22:00 и 23:00 UTC (= 00:00–01:00 по Берлину), попадали в предыдущий день. До 29.03 смещение совпадало, отсюда «часть дней в конце марта», а остальное сходилось. Результат вдобавок зависел от даты запроса: летом сломались бы уже дни до перехода.

**Как нашли:** при чтении `totals.ts`: смещение берётся от `new Date()`, а не от момента заказа. Таймзона `c_7` из API — `Europe/Berlin`, дата перехода попадает ровно в период жалобы, и в данных у `c_7` есть заказы в 22:40Z и 23:20Z почти каждый день.

**Альтернативные гипотезы.** Проверял пересчётом сумм `c_7` по дням на полной выгрузке API: нужна гипотеза, при которой до 27.03 всё совпадает, а расходится только часть дней 27–31.03.

| Гипотеза | Какие дни расходятся | Вердикт |
|---|---|---|
| Смещение на момент запроса, зимнее (+1) | 29, 30, 31.03 | совпадает с жалобой |
| То же, но запрос летом (+2) | 25–28.03 | та же ошибка, другая дата запроса |
| `createdAt` без зоны — местное время Берлина, а не UTC | все дни, включая 25–26.03 | отвергнута: другие дни тоже бы разошлись |
| Синк не забрал поздние заказы (`o_049xx+`, созданы задним числом) | 27–30.03 | похоже, но в прогоне синк забрал все 5030 заказов |
| Потеря копейки в `toKop` | — | на `total` не влияет: `amount` — целые рубли |

Остаётся слабое место, хотя в прогоне оно не проявилось: синк заканчивается на первой пустой странице или повторе курсора. Если API отдаст пустую страницу в середине ленты, поздние заказы потеряются.

**Исправление:** смещение считается для каждого заказа на момент `createdAt`. Тест — переход на летнее время в Berlin (на старом коде падает).

## 3. Вторая ошибка: гонка при параллельных вебхуках

**Как нашли.** Проверял гипотезу, что версия с тем же `updatedAt`, но другим содержимым отбрасывается как `stale`. Направил вебхуки мока на сервер, который просто пишет тела запросов, и прогнал их дважды. Оба прогона одинаковые: 92 вебхука по 21 заказу `c_7`, 55 точных повторов, 15 доставок не по порядку. Пар с равным `updatedAt` и разным содержимым нет — гипотеза отвергнута.

Но при сверке «самая новая версия каждого заказа ↔ строка в БД» 4 заказа из 21 разошлись: в БД лежала **не самая новая** версия. Например, `o_02131`: пришли версии 11:20 (скидка 10%) и 12:20 (33%), а сохранилась 11:20.

**Причина.** `OrdersService.apply` делал `get` → сравнение `updatedAt` → `save` тремя отдельными шагами. Мок шлёт вебхуки параллельно (92 штуки за 1,5 с). Два запроса читают одну и ту же старую строку, оба проходят проверку, и побеждает тот `save`, который закончился позже, — а не тот, чья версия новее.

**Влияние на отчёт.** У этих заказов менялась только скидка, поэтому `gross`/`total` не затронуты, а `net` за 27.03 и 31.03 был завышен: 21056.34 → 19855.51 и 31995.09 → 29787.55. Если бы в гонку попал переход `paid` ↔ `refunded`, поехал бы и `total`. Результат зависел от тайминга, то есть был невоспроизводим.

**Исправление.** Сравнение версий перенесено в один SQL-запрос: `INSERT … ON CONFLICT DO UPDATE … WHERE orders.updated_at < excluded.updated_at RETURNING (xmax = 0)`. Postgres блокирует строку на время upsert и проверяет `WHERE` по последней закоммиченной версии, поэтому старая версия больше не перезаписывает новую. Результат `created`/`updated`/`stale` определяется по тому, вставлена строка, обновлена или не тронута. Неиспользуемый `OrdersRepository.get` удалён.

**Тест:** 20 заказов, по каждому параллельно отправляются версии 13:00, 11:00, 12:00; должна сохраниться 13:00. На старом коде падает стабильно (3 из 3), на новом проходит.

**Попутно — копейки:** `toKop` делал `Math.floor(rub * 100)`, а `0.29 * 100 = 28.999…`, и копейка терялась (в данных так ведут себя, например, суммы вида `x.29`). Теперь сначала гасим погрешность float, потом отбрасываем доли копейки; прежнее поведение `toKop(10.999) = 1099` сохранено. Для `total` раньше это почти не проявлялось (суммы — целые рубли), а для `amountPaid` проявлялось бы регулярно.

## Как проверял

1. `npm run typecheck`, `npm test` — 37 тестов, все зелёные. Новые: скидки через вебхук и через синк, старый формат без `amountPaid`, `amountPaid > amount`, переходы на летнее и зимнее время (`tzOffsetMinutes` на границах и дни в `daily-totals`), погрешность float в `toKop`, параллельные версии одного заказа, миграция 002 на существующих строках (в отдельной схеме, транзакция откатывается).
2. `result.json` получен строго по шагам задания: `docker compose down -v && up -d`, миграции, `POST /sync` (52 страницы, 5030 заказов, 0 invalid), вебхуки (92, все 200), запрос `daily-totals`.
3. Независимая сверка: тот же агрегат в Postgres через `created_at AT TIME ZONE 'Europe/Berlin'` совпадает с `result.json` до копейки.
4. Выгрузил все заказы напрямую из внешнего API и сверил `amount_kop`/`paid_kop` в БД с точными десятичными значениями (строковый разбор, без float). Совпали все, кроме заказов, которые обновились вебхуками.
5. Тела вебхуков перехвачены отдельно (см. раздел 3). Для каждого из 21 заказа сверил «самую новую версию из выгрузки и вебхуков» со строкой в БД: после исправления совпадают все 21 (до исправления — 17).

## Что заметил

- `createdAt` у части заказов приходит без зоны (`"2026-03-29T00:30:30"`). Обрабатываем как UTC (по контракту и существующему коду).
- `amount` и `discountPercent` иногда приходят строками (`"5584.00"`, `"7"`).
- У 1177 заказов полей `discountPercent`/`amountPaid` нет вовсе.
- Вебхуки меняют скидку у уже оплаченных заказов (например, 0% → 33%) и приходят параллельно, с повторами и не по порядку.
- Rate limit API иногда приходит как `200 {"error":"rate_limited"}`; клиент это уже обрабатывает.

## Допущения

- `total` = `gross` (по заданию). `refunded` и `pending` не входят ни в одну сумму — как и раньше.
- Строки времени без зоны — UTC, как в контракте. Если на деле это локальное время клиента, суммы около полуночи поедут; проверить это можно только по отчёту платёжной системы.
- Доли копейки в `amountPaid` отбрасываются, как для `amount`; в данных их нет.
- При миграции существующие строки считаются без скидки. Чтобы подтянуть скидки на уже работающей БД, нужна пересинхронизация: повторный `/sync` сочтёт версии `stale`, потому что `updatedAt` не изменился.

## Что бы доделал

- Бэкфилл `paid_kop` для существующих данных (синк, перезаписывающий версии с тем же `updatedAt`).
- Хранить `discountPercent`, сверять с `amountPaid` и логировать расхождения, в том числе `amountPaid > amount`. Сейчас в сервисах нет логгера, а протаскивать его ради одного предупреждения не стал.
- Деньги в JSON строкой, а не float — обсудить с потребителями API.
